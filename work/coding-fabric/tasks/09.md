# Task 09: Ansible role `telegram-ai-agent`

## Required Skills
Before starting, load: /skill:ansible-automation

## Description
Install `pavel-molyanov/telegram-ai-agent` (upstream Python bot, MIT, reused as-is)
from a pinned commit that contains the `cwd:"DYNAMIC"` sentinel feature (produced by
the separate `mnemonic-tg-bridge` feature — upstream PR). Until the PR merges,
role pins to fork `mnemonic-org/telegram-ai-agent`. Wire systemd, per-topic configs
with `cwd:"DYNAMIC"`, env var pointing to workspace-manager (T08). Anchors tech-spec
D8, §2.3 role 11, user-spec AC6, AC8.

## What to do
- `roles/telegram-ai-agent/tasks/main.yml`:
  - install `uv` (via official installer, pinned version)
  - `git clone` from variable `telegram_ai_agent_repo` (defaults to upstream
    pavel-molyanov; switchable to fork) at `telegram_ai_agent_pin` (commit SHA or tag)
  - `uv sync --frozen` inside the cloned dir
  - render `/etc/telegram-ai-agent/.env` from sops with bot token, Deepgram key
    (optional), `TELEGRAM_AI_AGENT_CWD_RESOLVER_URL=http://{{ tailscale_ip }}:8080`
  - render `/etc/telegram-ai-agent/topics.yml` with 8 topics, each with
    `cwd: "DYNAMIC"`, engine per §2.4 matrix, exec_mode/stream_mode defaults
  - install systemd unit `telegram-ai-agent.service` with `Restart=on-failure`,
    `EnvironmentFile=/etc/telegram-ai-agent/.env`
  - sanity-check: bot replies to `/ping` in `ops` topic within 30s
- Defaults expose `telegram_ai_agent_repo` and `telegram_ai_agent_pin` as the two
  variables operator can flip when upstream PR merges (or when bumping versions)
- Fail-fast: if `TELEGRAM_AI_AGENT_CWD_RESOLVER_URL` not set OR pinned commit
  doesn't contain the DYNAMIC feature (probe via `uv run pytest tests/test_dynamic_cwd.py
  --co -q` returning 0), error with actionable message pointing to `work/mnemonic-tg-bridge/user-spec.md`

## Details
**Files:**
- `infrastructure/ansible/roles/telegram-ai-agent/{tasks,defaults,templates,molecule}/`
- `infrastructure/ansible/inventory/group_vars/all/telegram-ai-agent.yml` — pin
  variables (repo URL, commit SHA, fork toggle)
- `infrastructure/secrets/secrets.sops.yml` — extended with `TELEGRAM_BOT_TOKEN`
  (if not already there from T05) and optional `DEEPGRAM_API_KEY`

**Edge cases:**
- Upstream PR merges → operator flips `telegram_ai_agent_pin` to upstream tag and
  re-applies; idempotent rollout
- PR still open → defaults stay on fork; no operator action needed
- `uv sync` fails mid-install (network blip) → role retries 3x with backoff;
  on persistent failure → systemd unit not started, role exits non-zero
- Bot config schema drift between upstream and our pin → caught by `--check-config`
  step before service starts
- Per-topic config: schema fields are upstream-defined (`cwd`, `mode`, `engine`,
  `exec_mode`, `stream_mode`, `mcp_config`, `model`); we only set `cwd: "DYNAMIC"`
  and `engine` per topic; everything else uses upstream defaults

**Implementation hints:**
- Use `community.docker` NO — upstream bot is not dockerized; runs via uv-managed
  Python venv directly
- Pin `uv` version explicitly; do not auto-update
- systemd unit drops privileges to `op` user (Task 02); bot does not need root
- The `--check-config` step is the upstream feature gate — if it fails, the role
  fails loudly with a pointer to mnemonic-tg-bridge user-spec
